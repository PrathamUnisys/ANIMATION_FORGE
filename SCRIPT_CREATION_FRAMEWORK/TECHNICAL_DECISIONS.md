# Technical Decisions

**Date:** 2026-11-10  
**Status:** Initial design decisions; implementation has not started.

| Decision | Alternatives considered | Evidence / testing | Selected approach | Trade-offs / replacement path |
|---|---|---|---|---|
| Keep the first implementation isolated | Edit current `AGENTS/`, `SCHEMAS/`, `CORE/`, global pipeline; create a module alongside them | `CORE/CHANGE_CONTROL.md` requires formal registered and authenticated approval for protected paths. Existing docs are mixed proposal/implementation status. | New `SCRIPT_CREATION_FRAMEWORK/` module, with documented integration interfaces; do not edit protected shared files until an approved Change Request exists. | Duplicates some documentation temporarily. Later integrate by CR with compatibility/rollback plan. |
| Use stages plus artifact contracts, not an agent swarm | One large prompt; many specialist agents; one small coordinator with reusable role instructions | Current app already separates story analysis, outline/cards/script, critique/QC; task requests low proliferation. | Stage coordinator/data contracts; named roles are responsibilities and can initially be instructions/prompt components, not parallel agents. Independent reviewer must be a separate invocation/operator and receive no self-assessment. | Less parallel throughput. Replace role boundaries with separately orchestrated services only if tests show value. |
| Keep creative decisions human-gated | Auto-select concept, outline and final script; human chooses at consequential boundaries | Repository policy: agents propose, humans approve. Current pipeline already gates outline before scene cards/script. | Human chooses concept/architecture where alternatives differ and owns final approval. | More deliberate review time; preserves intent and canon. |
| Treat research as a provenance ledger | Source bibliography only; claim-to-source records; automated fact-check service | Ten-script reviews found attribution and scope defects even where source lists existed. No automatic fact verifier exists. | Stable claim IDs mapped to source locators, support status, scope, confidence/uncertainty and draft passage IDs. Research can be manual/web-assisted. | Adds maintenance and cannot algorithmically prove truth. Can export into future DB after governance review. |
| Keep facts and story artifacts separate | Put citations only at end of script; use claim records coupled to each line | Current source dossier is manual; existing research schema is broad technical R&D. | Dossier and claim ledger separate from narration, linked by IDs; each stage records source revisions and date. | More artifacts, but more traceability. Could later use a single bundle schema after data proves stable. |
| No numeric creative score gate | Score rubric and average; evidence-led findings | Existing documents conflict: a rubric asks 0–10 scores while other draft standards and critic contract prohibit score averages. Ten scripts cannot calibrate a threshold. | Severity + evidence + consequence + recommendation; no aggregate pass score. | Less convenient ranking; avoids false precision. Reconsider only after a human-approved calibration study. |
| Use distinct status labels | Generic `done`; one approval state for all work | Existing repository uses stage/approval statuses; ten-script report stresses estimates, not approval. | Separate artifact maturity (draft/review/revision/fact-check/human review/approved) from each check outcome and runtime evidence level. | State mapping needs careful documentation; integrate with existing status enums only by compatibility review. |
| Deterministic checks stay narrow | Use LLM to validate everything; infer quality from generated map; build broad custom runtime | Existing QC uses actual input checks but simple text patterns; current runtime standard requires explicit assumptions. | Use deterministic code only for exact computable invariants. LLM outputs are proposals; reviewers inspect reasoning; no “fact check pass” from parsing. | Cannot catch nuanced semantic errors. Add supported checkers only with evidence and false-positive testing. |
| Reuse current runtime standard, refine for single voice | Word-count-only estimate; fixed target wpm; mark estimate as measured | Existing runtime standard distinguishes estimate vs measured; prior experiment reports narration words, pace and planned holds. | Count narration only, state pace assumption, add separately planned holds, compute range, retain `SCRIPT_ESTIMATE`; measure after recording/animatic. | Estimate varies by narrator/edit. Provide per-scene model for production, not a universal pace. |
| Validation library choice deferred until prototype | No validator; hand-written validators; `jsonschema` Draft 2020-12 | Existing schemas declare Draft 2020-12. No live validation was run during this design phase. | Backlog includes a true validator run against the selected module schema and syntax parser as separate operations. Avoid editing shared schemas. | Dependency decision based on installed/runtime environment and test evidence during implementation. |
| Do not promise platform prediction | Predicted retention scores; editorial maps only; analytics import | Official YouTube guidance exposes video-level analytics, ambiguity in spikes/dips, and A/B/C watch-time outcomes. No video in prior experiment was published. | Retention map is intended progression; actual performance learning requires recorded/published output and measured data. | The framework cannot promise virality or performance; analytics connector can be added later under scope/consent review. |
| Preserve narration accessibility | Simplify subjects for children; retain complex vocabulary; plain-language without loss of depth | User-approved language rule and prior script experiment; reviews most often flagged scope/orientation/repetition, not mature themes. | Plain spoken English, explain necessary terms, retain adult ideas. Accessibility is editorial review, not a fake automated grade. | Human read-aloud check required; possible future comprehension study. |
